根据这些机制，当前方案可能出现以下情况：

1. **私有内核连接节点服务器时，被 TUN 接管。**

   网络路径可能变成：

   ```text
   Claude → 私有 Mihomo → Clash Verge TUN → 节点服务器 → 目标网站
   ```

   Clash Verge 随后按照自己的规则，将这条连接直接发送出去，或者经过它选中的代理节点。因此，Clash Verge 重载、重启、退出时，仍可能导致连接中断。

2. **DNS 解析受到影响。**

   即使私有内核配置了自己的 DNS，DNS 请求也需要经过系统网络。其请求仍可能被路由进入 TUN；使用系统 DNS 时，还可能收到 Clash Verge 提供的 fake-IP，产生额外依赖。实际结果取决于 DNS 协议、路由和劫持设置。[官方 DNS 文档](https://wiki.metacubex.one/config/dns/)

3. **部分应用子进程可能直接使用 Clash Verge。**

   如果某个子进程没有遵守代理参数或环境变量，其直接发出的连接可能被 TUN 接管。此时，同一个应用的不同连接可能经过不同节点。

4. **最终出口 IP 不一定改变。**

   如果 TUN 接管的是“私有内核连接节点服务器”的连接，目标网站通常仍然看到私有节点的出口 IP；增加的中间转发仍可能带来延迟和断线。绕过私有内核的子进程连接，则可能使用 Clash Verge 的出口。

此前方案按关闭 TUN 的条件设计，尚未验证上述路径，因此开启 TUN 后，无法承诺 Clash Verge 切换、重启和退出期间两个专属通道持续正常。
